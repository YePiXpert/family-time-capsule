# 升级到 v1.0：数据库安全与回滚

本文适用于从最后一个 `v0.1.3` 数据库（迁移 `0010`）向当前版本以及最终
`v1.0.0` 升级。发布前仍应以 `docs/DEPLOYMENT_CHECKLIST.md` 为总清单；本文只
描述数据库升级边界。

## 不变量

- `0000`–`0010` 是已经发布的历史，禁止修改、重排或删除；新结构只能追加迁移。
- 数据库与 `$DATA_DIR` 中的原件共同组成档案。只复制 SQLite、漏掉原件不是备份。
- SQLite 处于 WAL 模式时，运行中直接复制 `capsule.sqlite` 可能漏掉已经提交但仍在
  `capsule.sqlite-wal` 中的数据。
- 不支持向下迁移。要把应用退回旧版本，必须同时恢复该旧版本升级前的数据库快照。
- 新旧版本都不得改变原件；`capturedAt` 与 `importedAt` 始终是两个独立字段。

## 启动时会自动做什么

数据库连接位于 `$DATA_DIR/db/capsule.sqlite`。启动发现“已有业务数据，且代码中有
待执行迁移”时，程序会在执行第一条待迁移 SQL 之前：

1. 使用 SQLite `VACUUM INTO` 创建事务一致的副本，因此已提交的 WAL 页面也会进入
   快照；
2. 对副本执行 `PRAGMA integrity_check`；
3. 刷新文件内容，并从唯一的 `.partial` 临时名原子改名为：
   `$DATA_DIR/backups/pre-migration/capsule.pre-migration.<时间>.<UUID>.sqlite`；
4. 然后在 Drizzle 的迁移事务中执行所有待迁移 SQL。

以下情形不会制造无意义的快照：全新空库、已经处于最新版本的数据库。若数据库迁移
时间戳比当前代码所知的最新迁移还新，程序会拒绝打开，防止旧代码误写新数据库。

迁移失败时，启动会失败并在错误信息中打印可恢复快照的绝对路径；SQLite 连接会关闭，
不会继续提供半升级实例。迁移事务会回滚，但仍应保留快照，直到故障原因确认。

## 升级前

1. 停止所有会写入该档案的应用实例和后台任务。
2. 另做一份完整的 `$DATA_DIR` 离线备份（数据库、原件、衍生物和导出）；自动快照是
   迁移回滚点，不替代完整灾备。
3. 确认备份可读，并记录当前应用版本、数据库文件路径和备份位置。
4. 确认卷上至少能再容纳一个当前 SQLite 数据库；空间不足会让快照阶段直接失败。
5. 先在完整备份的副本上演练相同版本升级，再升级唯一的生产档案。

## 升级后验收

至少检查：

- 应用健康检查通过，日志中只有一次 `created WAL-consistent pre-migration snapshot`；
- 家庭、人物、时间轴、事件详情、贡献、事实和胶囊数量符合升级前记录；
- 抽查原件可以打开，导出能够完成且媒体 SHA-256 校验通过；
- `PRAGMA integrity_check` 返回 `ok`，`PRAGMA foreign_key_check` 无记录；
- 新增收件箱来源关联不篡改旧数据：旧 `v0.1.3` 收件箱记录的
  `memory_event_id` 合法地保持为空。

保留升级前快照和完整离线备份，直到上述检查全部完成并经过一个稳定观察周期。快照
不会被应用自动删除；清理属于管理员明确执行的保留策略。

## 迁移失败后的恢复

1. 保持应用停止。不要在运行中复制或替换数据库。
2. 从启动错误中取得准确的 `snapshotPath`，先把失败现场的
   `capsule.sqlite`、`capsule.sqlite-wal`、`capsule.sqlite-shm`（若存在）移动到一个
   单独的故障调查目录；不要覆盖或删除它们。
3. 对快照运行 `PRAGMA integrity_check`，确认结果为 `ok`。
4. 把已验证快照复制为 `$DATA_DIR/db/capsule.sqlite`。确认目标目录中没有来自失败现场的
   同名 `-wal` / `-shm` 文件。
5. 启动与该快照版本匹配的应用，先做只读验收，再恢复写入。

若迁移已经成功，但业务验收失败，同样必须停止应用并恢复升级前快照，不能只把容器或
代码退回旧版本。数据库版本超前保护会主动拒绝这种不安全组合。

## 自动化证据

- `tests/integration/migration-safety.test.ts` 覆盖空库无快照、包含未 checkpoint WAL 数据的
  一致快照、迁移失败后的可恢复快照与句柄释放，以及数据库版本超前拒绝。
- `tests/fixtures/v0.1.3/generate-fixture.mjs` 固定 `0000`–`0010` 的标准化 SHA-256 和时间戳，
  构建带核心关系及真实媒体哈希的 `v0.1.3` SQLite 档案。
- `tests/integration/upgrade-v013.test.ts` 将该档案升级到 `HEAD`，验证行数、外键、人物/账号
  关系、原件哈希、时间轴顺序、详情关系、收件箱兼容性及完整导出。

每追加一条 v1 迁移，这组 `0010 -> HEAD` 测试都必须继续通过；不得通过改写历史迁移来
“修复”升级测试。
