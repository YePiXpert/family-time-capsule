# Repository workflow

- For UI work, read `DESIGN.md` and apply its mobile design rules through the shared theme and components.
- Product scope lives in `PRODUCT.md` (positioning, principles, non-goals, the three questions, roadmap order). Read it before planning or reprioritising a feature; if a feature contradicts it, change `PRODUCT.md` with the owner first, then build. Anything that touches AI prompts follows `docs/AI-PROMPTS.md` (principles, shared preamble, full prompt drafts, what the phone sends, how to verify).
- Work and release only from `main`; do not create feature, fix, release, or temporary build branches.
- Before starting, run `git checkout main`, `git pull --ff-only origin main`, and inspect `git status --short`.
- Commit small, clear milestones and push them to `origin main` by default.
- Do not create pull requests and never force-push.
- Before pushing, run the local quality gate (`npm test` and `npm run typecheck` in `mobile/` and `server/`; `npm run lint` in `mobile/` — the server has no lint script) so pushes are green by default; do not wait on or poll GitHub Actions after routine pushes. Check the latest `main` CI run only when starting new work or preparing a release — if it is red, repair it directly on `main` and push.
- For release or verification builds being tracked, including tag builds and `mobile-build.yml`, choose the waiting policy by the main model. Report the run URL, full source SHA, and known status when tracking starts:
  - **All models except Fable (including unknown models):** poll the tracked run through completion by default, then verify the result and finish delivery. Keep status checks spaced out (30–60 seconds) and provide concise progress updates while waiting.
  - **Fable:** do not poll by default. If the environment supports explicitly selecting an Opus sub-agent, Fable may delegate polling to one Opus agent, passing the run URL and full source SHA. That agent follows the default polling policy even though the main model is Fable, and reports the final run/job status and source/artifact verification evidence. Fable waits for its completion notification without duplicating status queries, then reviews the evidence and remains responsible for README/HANDOFF updates and artifact delivery. If the session cannot continue waiting, record the pending run and remaining verification work for resumption; delegation alone never counts as delivery. Do not substitute another model for the Opus polling agent. If Opus is unavailable or delegation fails or is not used, use the no-polling fallback.
  - **Fable-only no-polling fallback:** report the run URL, full source SHA, known status, and remaining verification work, then end the turn when independent local work is done. Do not use `gh run watch`, repeated status queries, sleep loops, scheduled wakeups, or background agents to wait. Resume verification only after a completion notification arrives or the owner explicitly asks for a status check; check once and, if still running, report that and end the turn.
  - Routine milestone pushes still must not be polled. An explicit owner instruction about monitoring overrides these defaults. Read relevant failure logs only after a failure is confirmed. Complete result-dependent README/HANDOFF updates and artifact delivery after completion is verified; never describe a pending, failed, or cancelled build as successful.
- Network calls live only in `mobile/src/sync/transport.ts`, `mobile/src/ai/client.ts` and `mobile/src/family/api.ts`; `mobile/src/local` never touches the network. The remote side stores ciphertext only. The family content key stays on approved devices; it leaves a phone only sealed to one approved device's public key (HPKE, bound to family, member, device and pairing request) or wrapped under the family recovery secret, and the server never holds it in the clear. The recovery secret is independent of the content key, is shown once to an admin, and is never stored on any device or server. `mobile/scripts/verify-local-boundary.py` enforces the network files, the local/sync separation and the single service address in `brand.ts`. Current design: `docs/ARCHITECTURE.md` (the original plan is archived in `docs/history/`).
- Mobile is the primary usage target. When the owner explicitly requests an installable release, deliver it from the selected `main` commit (full source SHA). Before dispatching `mobile-build.yml`, check for an existing run for that exact source SHA, including a tag-triggered run: reuse a queued/running run, or a successful run whose required artifacts are still available, and follow the waiting policy above. Do not dispatch a duplicate build merely because the existing run was triggered by a tag. If no usable run exists, dispatch a build or rerun the appropriate failed/cancelled run after reviewing its outcome. Verify all required jobs and artifact source/version metadata before providing the Android APK and unsigned device IPA for the owner to self-sign. Increment native build numbers once per release, not per retry or redispatch. Routine milestone pushes do not require a mobile build.

- Never disclose credentials or actual deployment/upstream endpoint values in replies, logs, or deployment documentation. Keep operational values in private server configuration; use environment variable names or placeholders in examples. Do not print secrets when inspecting configuration.
