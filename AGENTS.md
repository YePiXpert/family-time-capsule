# Repository workflow

- For UI work, read `DESIGN.md` and apply its mobile design rules through the shared theme and components.
- Product scope lives in `PRODUCT.md` (positioning, principles, non-goals, the three questions, roadmap order). Read it before planning or reprioritising a feature; if a feature contradicts it, change `PRODUCT.md` with the owner first, then build. Anything that touches AI prompts follows `docs/AI-PROMPTS.md` (principles, shared preamble, full prompt drafts, what the phone sends, how to verify).
- Work and release only from `main`; do not create feature, fix, release, or temporary build branches.
- Before starting, run `git checkout main`, `git pull --ff-only origin main`, and inspect `git status --short`.
- Commit small, clear milestones and push them to `origin main` by default.
- Do not create pull requests and never force-push.
- Before pushing, run the local quality gate (`npm test` and `npm run typecheck` in `mobile/` and `server/`; `npm run lint` in `mobile/` — the server has no lint script) so pushes are green by default; do not wait on or poll GitHub Actions after routine pushes. Check the latest `main` CI run only when starting new work or preparing a release — if it is red, repair it directly on `main` and push.
- For dispatched release or verification builds, including tag builds and `mobile-build.yml`, choose the waiting policy by the main model:
  - **Claude Opus:** poll the dispatched run through completion by default, then verify the result and finish delivery. Keep status checks spaced out (30–60 seconds) and provide concise progress updates while waiting.
  - **Fable:** do not poll by default. If the environment supports explicitly selecting an Opus sub-agent, Fable may delegate build polling to that Opus agent; pass the run URL and full source SHA, and have it report the final status and verification evidence. Do not substitute Fable or another model for the Opus polling agent. If Opus is unavailable or no delegation is made, report the run URL and known status, then end the turn when independent local work is done.
  - **Other or unknown models:** use the same no-polling fallback. In that fallback, do not use `gh run watch`, repeated status queries, sleep loops, scheduled wakeups, or background agents to wait. Resume verification only after a completion notification arrives or the owner explicitly asks for a status check; check once and, if still running, report that and end the turn.
  - Routine milestone pushes still do not require polling CI. An explicit owner instruction about monitoring overrides these defaults. Read relevant failure logs only after a failure is confirmed. Complete result-dependent README/HANDOFF updates and artifact delivery after completion is verified; never describe a pending build as successful.
- Backup transport lives only in `mobile/src/sync`; `mobile/src/local` never touches the network; the remote side stores ciphertext only, and the key leaves the phone only as the 12-word recovery code. `mobile/scripts/verify-local-boundary.py` enforces the first two rules and the single service address in `brand.ts`.
- Mobile is the primary usage target. When the owner explicitly requests an installable release, deliver it from the delivered `main` commit: dispatch and verify `mobile-build.yml` (full source SHA), provide the Android APK and the unsigned device IPA for the owner to self-sign, and increment native build numbers once per release. Routine milestone pushes do not require a mobile build.

- Never disclose credentials or actual deployment/upstream endpoint values in replies, logs, or deployment documentation. Keep operational values in private server configuration; use environment variable names or placeholders in examples. Do not print secrets when inspecting configuration.
